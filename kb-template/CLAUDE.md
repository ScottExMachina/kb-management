# Personal Knowledge Base Schema

> **Do not edit this file.** It is owned by the `kb-management` plugin and is refreshed whenever you run `/kb-setup`. Read it for context, but never modify it.

This is the schema for a personal knowledge base.

Claude Code reads this file at the start of every session to understand the structure, operational boundaries, and workflows. The skills that operate on this KB (`kb-ingest`, `kb-query`, `kb-lint`, `kb-lookup`) are provided machine-wide by the `kb-management` plugin — they are not stored inside the KB.

## Directory Structure

```text
<kb-root>/
├── .claude/
│   └── CLAUDE.md              # This file (the schema)
├── kb.config.md               # KB marker + version + domain — do not delete
├── index.md                   # Content catalog — updated on every ingest
├── log.md                     # Append-only operation record
├── ingest/                    # Staging area — files queued for ingestion (transient)
├── raw/                       # Permanent archive of ingested sources (never modified)
├── sources/                   # Source summary pages
├── pages/                     # All named things: concepts, people, orgs, products
└── notes/                     # Personal notes — DO NOT MODIFY WITHOUT PERMISSION
```

The presence of `kb.config.md` at the root is what marks this folder as a KB; the skills check for it before acting.

## Boundaries

**You operate within `ingest/` (read and move), `raw/` (write via move from ingest only), `sources/`, `pages/`, `index.md`, and `log.md` (read and write). You may read and reference files in `notes/` but do not write there unless the user explicitly instructs you to in the current session. These are user-generated and managed notes.**

## Naming Conventions

- Filenames: lowercase, hyphenated (`transformer-architecture.md`)
- Wikilinks: `[[filename|Display Text]]` — e.g. `[[ace-framework|ACE Framework]]`
- Dates: ISO 8601 (`2026-05-10`)
- Tags: lowercase, hyphenated

## Category System

Every page in `pages/` gets exactly one **category** and a small set of **tags**. These answer different questions and must not duplicate each other.

- **Category** answers: *what kind of thing is this?*
- **Tags** answer: *what is it about, and what does it connect to?*

### Categories

| Value | Use when the page is about... |
|---|---|
| Concept | An abstract idea, principle, theory, or phenomenon |
| Method | A framework, methodology, approach, pattern, or process |
| Tool | A specific software product, platform, or application |
| Work | A book, paper, article, or other intellectual work as a subject |
| Person | An individual |
| Organization | A company, institution, or team |
| Place | A location, market, or region |
| Event | An occurrence, milestone, development, or launch |
| Reference | Lookup or navigational material |

### Tags

Use 3–6 tags per page drawn from two dimensions:

- **Domain** — the field or area this belongs to (e.g. `pkm`, `ai-strategy`, `product-management`)
- **Association** — tools, platforms, or organizations this page connects to (e.g. `claude-code`, `obsidian`)

Three rules:
1. Never use a tag to restate the category — no `tool`, `method`, `reference`, etc. as tags
2. For **Tool** pages, tags describe what kind of tool (`memory`, `search`, `open-source`); for all other pages, tags name associated tools (`claude-code`, `obsidian`)
3. Use wikilinks — not tags — for people and organizations that have or should have their own page

## Page Templates

### Source Summary (`sources/`)

```markdown
---
title: [Title]
type: summary
source: raw/[filename]
date: YYYY-MM-DD
tags: []
---

# [Title]

**Source:** [Author(s), Publication, Date]

## Summary

[Key content in your own words]

## Key Points

-

## Related Pages

- [[concept-or-entity|Concept or Entity]]
```

### Page (`pages/`)

Use this for concepts, people, organizations, products, or any named thing worth its own page.

```markdown
---
title: [Title]
type: page
category: [Category]
sources: []
updated: YYYY-MM-DD
tags: []
---

# [Title]

[1–2 sentence definition or description]

## Overview

[Substantive explanation, updated as new sources are ingested]

## Relationships

- Related to: [[other-page|Other Page]]

## Sources

- [[source-summary|Source Summary]] — [what this source contributed]

## Open Questions

-
```

### index.md Format

```markdown
# Knowledge Base Index

*Last updated: YYYY-MM-DD — [N] pages*

## Sources

- [Title](sources/title.md) — one-line summary

## Pages

- [Title](pages/title.md) — one-line summary
```

### log.md Entry Format

```text
## [YYYY-MM-DD] operation | Description

- Brief note on what was ingested/queried/linted
- Pages created: N, pages updated: N
- Notable: any contradictions found or resolved
```

## Skills

Knowledge base management is handled by the `kb-management` plugin's skills (installed machine-wide, not copied into this KB). Invoke them from within this KB project session:

- `/kb-ingest` — ingest a new source from `ingest/`
- `/kb-query` — query this knowledge base and synthesize an answer
- `/kb-lint` — validate structure, find gaps, and manage migrations

A fourth skill, `kb-lookup`, queries any KB by path (used for cross-KB lookup from other sessions or agents). Plugin-level changes to these skills arrive via `/plugin update kb-management`; per-KB scaffolding changes arrive via `/kb-setup`.
